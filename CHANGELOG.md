# Changelog

## v4.0.0

- **Built-in core pinned to the latest release, 2.38.0** — `scripts/sync-mmcore-source.ts` (run by `postinstall` and `build:00-sync-mmcore-source`) syncs a pinned `BUILT_IN_CORE_VERSION`, now the latest MagicMirrorOrg release 2.38.0, and calls the GitHub API only with the new `--latest` flag. It used to sync the latest stable release whenever `mmcore-source/` was empty, so a fresh checkout (CI) built on 2.38.0 while existing checkouts stayed on 2.36.0, and `npm ci` failed whenever the GitHub API rate limit was reached. The pin keeps every build deterministic; it is bumped by hand on a new release. Because the stage runs the built-in core itself, the fixture module is split:
    - `tests/_fixtures/MMM-TestModule/` no longer overrides `getDom`, so the core's base `getDom` renders its template on every version. Its post-render work (binding the helper ping button, recording a `renderSnapshot`) moves to `MODULE_DOM_CREATED`/`MODULE_DOM_UPDATED` and leaves the markup untouched, so `updateDom()` with unchanged data still keeps the same DOM node. The transversal suites mount it and no longer branch on whether the fixture renders on a core; the "module that throws in getDom" tool test now gives the fixture a throwing `getDom` explicitly.
    - `tests/_fixtures/MMM-TestModule-super-getdom/` keeps the previous fixture verbatim, whose `getDom` awaits `this._super()`. The pinned suites mount it through `openPinnedStage`, so their D1 assertions are unchanged. `gotoSandbox()` takes a `fixture` option for it (`"default"` or `"super-getdom"`); a pooled server is reused only for the same variant.
    - The CI `core-matrix` job adds 2.36.0, so the 2.36.0 pinned suite still runs on its own core.
    - The unit contracts that assumed the 2.36 core now follow the built-in one: `js/class.js` is expected in the helper shims only when the core ships it (removed in 2.37), and the `node_helper` secret test seeds `global.configRedacted` as the helper runtime does, since 2.38 restores only the placeholders in the module's own config. The version-switch test tells the pre-switch stage document apart by a marker, so a switch to an mmvm copy of the built-in release is detected too.
    - `client/fonts/` takes the Roboto files 2.38.0 ships.
- **Dependency security update** — `@fastify/static` moves to `^10.1.8` and the lockfile takes the non-breaking `npm audit fix` updates (fastify, ws, socket.io-parser, engine.io, zod, fast-uri, find-my-way, moment, js-cookie), so `npm audit --omit=dev --audit-level=high` passes again. `@fastify/static` 10 required these changes:
    - `setHeaders` now receives the Fastify reply, so `/__harness/` sets `Cache-Control` with `reply.header`.
    - Its routes answer a doubled slash with 403, but the core requests module files as `modules/<ModuleName>//<file>`. The stage now serves the mounted module through a route that collapses empty segments, as `express.static` does on a real mirror.

- **The viewport runs the real MagicMirror core of the active version** — the stage iframe no longer runs the sandbox's hand-ported 2.36 browser runtime. It loads the active version's own `index.html`, `js/`, `css/`, `translations/` and vendor files, served verbatim under `/__stage/`, with only the core's own `#VERSION#`/`#TESTMODE#` substitutions and one injection point (the stage observer script, the stage state and the isolation stylesheet). Switching versions in MM Version now changes the viewport too: frontend and backend always run the same version, including `develop`, so a module that calls `this._super()` in `getDom` fails on 2.37+ and `.mjs` scripts load from 2.37, as on a real mirror. Details:
    - `config/`, `config/basepath.js` and `js/positions.js` are generated in memory per version; `env`, `startup`, `version` and `cors` run the version's own `server_functions.js` handlers; the mounted module is served at `/__stage/modules/<ModuleName>/`.
    - The `config` global is the real MagicMirror config (the version's defaults, the sandbox language and locale, `basePath: "/__stage/"` and the saved module envelope), which removes the old limitation to `language`, `locale` and `basePath`.
    - Only the module's region and its ancestor containers are visible, inside the core's real DOM and CSS; the region keeps the core's own geometry, so module screenshots now show the module where MagicMirror places it in a window of that size.
    - The module's `node_helper` talks to the core over `/__stage/socket.io`, and its traffic feeds the WebSocket panel from the server side.
    - Saves, restarts, watcher reloads and version switches reload the stage exactly once, through the core's own `RELOAD`; the shell reloads the frame only when no core page listens, or after a 5 s fallback. The version badge names the core the viewport reports.
    - Every tool keeps working on the real core: lifecycle controls, notification emit and log, WebSocket, console and helper logs, config save-and-reload, the language switch, and Refresh styles, which now re-fetches the module's own `modules/<ModuleName>/` stylesheets in place. A hook point a version lacks is named in its panel.
    - Lifecycle semantics are the core's own on every version, asserted by the pinned D5 suites: `module.hidden` changes synchronously on `show()` and `hide()`, and `lockStrings` veto a show, are registered once, are cleared by `force`, and report `LOCK_STRING_ACTIVE` to `onError`, whether the module calls `this.show()` or `MM.showModule`.
    - Two hand-port divergences disappear with the hand-port: an empty or missing header no longer shows the module name (the core hides it, D6), and `MM.getModules().withClass("<module name>")` now matches the module, because the core adds the module name to its classes (D9). The module wrapper id is the core's own (`module_0_<ModuleName>`).
    - Removed: the hand-port runtime (`client/runtime/module.ts`, `lifecycle.ts`, `notifications.ts`, `assets.ts`, `translations.ts`, `client/runtime.ts`), the hand-port stage page (`server/templates/stage-page.eta`, `partials/stage-viewport.eta`), the routes that only served it (`/moment.js`, `/moment-timezone.js`, `/croner.js`, `/animate.css`, `/font-awesome.css`), the assets only it used (`client/styles/magicmirror-stage.css`, `client/styles/font-awesome.css`, the copied hand-port vendor scripts, and the Font Awesome fonts in `client/fonts/`; the asset sync now generates only the shell's Roboto sheet `magicmirror-fonts.css`), and the temporary maintainer flag `--real-core-stage` with its `HarnessConfig.realCoreStage`. `/__harness/stage` now redirects to `/__stage/`. The hand-port suites `tests/integration/core-fidelity.browser.test.ts` and `tests/unit/client/runtime-core-contracts.test.ts` are deleted; their contracts live in the version-pinned and transparency suites.
    - Distribution installs run the same path: `build:30-dist` packages the built-in core's browser files as `dist/core/` (`index.html`, `js/`, `css/`, `translations/`, the `defaultmodules/` support files, `favicon.svg`, and every vendor file the core page references, in a hoisted `node_modules/` layout), plus the `undici` and `ipaddr.js` bundles its `server_functions.js` needs. The built-in core resolves to `dist/core/` when `mmcore-source/` is absent, without the build-only `scripts/shared.ts`. The packaged-install e2e boots it in a browser.
- **Per-version fidelity suites and a CI core matrix** — the core-fidelity checks now come in two kinds. Cross-version transparency tests must pass identically on every core. Version-pinned suites (`tests/integration/core-fidelity/pinned/2.36.0` and `2.38.0`) hold D1, D3–D9, the D5 lockString cases, `.mjs` script loading and `configDeepMerge` array handling, each annotated with the file:line in that version's core. Each pinned suite runs on its own core through public behaviour only, and is skipped when that core is not available. For example, D1 resolves `this._super()` on 2.36.0 and fails with `TypeError: this._super is not a function` on 2.38.0. A new CI job, `core-matrix`, installs 2.36.0, 2.37.0 and 2.38.0 through the sandbox's own mmvm (`scripts/install-test-core.ts`; the release install is cached, the shims are rebuilt every run) and runs the integration and UI suites with `MM_SANDBOX_TEST_CORE_VERSION` set to that version, so the tool, isolation and badge suites run on each core too, and 2.37.0 covers the hybrid layout (classic `basepath.js`/`positions.js`, ES module `main.js`/`module.js`). A non-blocking entry does the same for `develop`. A requested core that is not installed now fails the run instead of silently running on the built-in core only.
- **Stage follows a reinstalled core, and serves less** — fixes from the final review of the per-version stage:
    - Redownload and Delete cache now forget the core's server code already loaded in the sandbox process (`server/stage/core-cache.ts`): its `require.cache` entries and its express sub-app. A redownloaded `develop` therefore serves its new `js/defaults.js` in `/__stage/config/` and its new `server_functions.js` endpoints without a restart, matching the new browser files.
    - The 5 s reload fallback is cancelled when the old stage document starts unloading (`pagehide`), not when the new one finishes loading. A slow core page no longer boots twice.
    - Stage reloads carry a reload generation. The server bumps it before each stage `harness:reload` and the core's `RELOAD`, and embeds the current one in every stage page (`StageState.reloadGeneration`). The shell ignores a core-driven `harness:reload` whose generation the stage page already carries: the event reached the shell late, after the stage had reloaded for it. When a page with an earlier generation loads instead, the shell reloads the frame once more. Before, a save made less than a second after another reload (a language change, for example) could leave the stage on the previous config: the core's `RELOAD` went to the unloading page, and the shell took its own event for the earlier reload and ignored it. The generation starts at the process start time rather than 0, so it keeps growing across sandbox restarts and a shell left open never mistakes a new reload for one its stage page already has.
    - On 2.38+ the stage observer waits for the core's own `MM`, however late it arrives. 2.38's `js/main.js` module graph has a top-level await (`js/socketclient.js` awaits the socket.io client import), so with a slow socket.io client the stage document loads before `main.js` has run. The observer now keeps its transparent `MM` capture until the core assigns `MM`; before, it dropped the capture at `DOMContentLoaded`. A disabled module now reports `bootComplete` only once the page has loaded and the core has provided `MM`; before, it did so on the document's `load` alone. A core that never provides `MM` never completes its boot, as with an enabled module that never gets `DOM_OBJECTS_CREATED`. A snapshot request no longer resets a completed disabled boot to pending, so the shell's `bootComplete` now stays true for a disabled module on every core.
    - `/__stage/node_modules/` serves only what the core's own `js/server.js` serves: the `js/vendor.js` packages plus `animate.css`, `@fontsource`, `@fortawesome` and `suncalc`. It used to serve any package Node could resolve from the core root, which in a distribution install is the consumer project's whole dependency tree.
    - Core static paths with an NTFS stream (`:`) or a trailing dot or space are refused, and `config/config.js` / `config/config.env` are also refused under their canonical file-system name, so Win32 aliases and links cannot reach them.
    - The Console panel serializes object arguments in a later task, so a logged object's `toJSON`, getters or Proxy traps no longer run inside the module's own `console.*`/`Log.*` call.
    - `docs/config.md` explains how the stage serves `**SECRET_*` placeholders per version.
- **MM Version warns about unreviewed core changes** — each cached version row in the MM Version domain shows `Unreviewed core change: <pieces>` when that version's `/config` handler, `loadConfig` secret redaction, `getHtml`, or `config/basepath.js`/`js/positions.js` writers no longer match a reviewed snapshot in `scripts/upstream-snapshots/core/` (typical on `develop`). This is groundwork for the per-version stage: the stage then falls back to the newest reviewed variant of that piece.
- **Superpowers working files stay local** — `.superpowers/` and `docs/superpowers/` (brainstorm sessions, design specs, plans) are gitignored and excluded from the npm package via `!docs/superpowers` in `files`, since `files` otherwise publishes all of `docs/`.
- **Quality runs the official dependency integrations** — `npm-check-updates` (`--jsonUpgraded --cooldown 7d`) and `npm-deprecated-check` (`ndc current`) now run after the ESLint pass, as in the official check. They are enabled by default and keep its issue budget: skipped once 4 issues exist, and the deprecated check once 3 do. This is a port of upstream `applyDependencyIntegrations`, guarded by `scripts/upstream-snapshots/dependency-integrations.txt` and `default-analysis-config.txt`. Both tools are now runtime dependencies at the upstream ranges, and their bins run from the sandbox's own `node_modules` instead of through `npx`.
- **Quality skips repository-ignored paths** — a deliberate local deviation. The official check analyzes a clean clone, while a local working tree also holds ignored files (build output, tool caches, `config.sandbox.json`), which caused false findings such as JSHint hits inside `.codegraph/`. Ignored paths come from `git ls-files --ignored --exclude-standard`, which covers nested `.gitignore` files, `.git/info/exclude` and the global excludes. Non-git modules fall back to the root `.gitignore`. Both the text analyzer and the ESLint pass apply the exclusion.
- **Quality runs the official ESLint pass** — the official MagicMirror-3rd-Party-Modules check now runs two passes: the text analyzer and an ESLint pass driven by `eslint.testconfig.js`. In October 2026 upstream moved ~30 checks (legacy HTTP clients, `node:` protocol, deprecated Node APIs, `XMLHttpRequest`, workflow action/Node versions) into that ESLint pass, so the sandbox had silently stopped reporting them. The sandbox now:
    - vendors `javascript-check.ts`, `http-import-check.ts`, `workflow-yaml-check.ts` and the full `eslint.testconfig.js` (as `eslint-testconfig.ts`, with only its plugin import path rewritten);
    - ports `runEslintCheck` from `pipeline/workers/process-module.ts` into `server/official-eslint-check.ts`, with the official defaults (`groups.deep` and `integrations.eslint` both `true`) and the same issue merging;
    - never executes repository ESLint configs or inline directives;
    - makes `build:02-sync-analyzer` fail when the ported `runEslintCheck`, its call site or `check-groups.config.json` change upstream (reviewed snapshots in `scripts/upstream-snapshots/`).

    New runtime dependencies, matching upstream ranges: `eslint`, `@eslint/js`, `globals`, `eslint-plugin-n`, `eslint-plugin-yml`, `eslint-plugin-depend`, `eslint-plugin-import-x`, `eslint-plugin-package-json`.

- **Quality analyzer vendoring** — `rule-registry.ts` from MagicMirrorOrg/MagicMirror-3rd-Party-Modules imports `workflow-version-policy.ts`, a file added upstream in October 2026 that the sync did not fetch. Packaged installs crashed at boot with `Cannot find module './workflow-version-policy.cjs'`, which made the `devdep-smoke` e2e fail. The file is now vendored and gitignored. `build:02-sync-analyzer` also fails fast when a vendored file imports an unvendored sibling, instead of breaking at runtime.
- **MagicMirror 2.37+ and upstream develop shims** — `build-node-compat.ts` treats `class.js` as optional (core removed it in 2.37.0), so shims now build for 2.37.0, 2.38.0 and 2.39.0-develop. Previously they failed with `Required MM source file missing: js/class.js`.
- **Bundled `ipaddr.js` for helper shims** — `server_functions.js` requires `ipaddr.js` for SSRF protection, but only `express` and `undici` were bundled into the shims' `node_modules`. Built-in shims found it through the sandbox package's own `node_modules`. mmvm shims under `~/.mmvm/shims/<version>/` have no parent `node_modules`, so any mmvm-activated version failed to load `node_helper`. The three packages now go through one `bundleCoreDependency` helper.
- **`node_helper` postlude delegates to core** — the postlude no longer replaces `setSocketIO`/`sendSocketNotification` with a 2.36-era copy. It clears the previous helper instance's `connection` listener (needed for in-process restarts) and calls the core `setSocketIO`, so the 2.38.0 per-module secret allowlist applies. The helper runtime now seeds `global.configRedacted` from the mounted module config, which 2.38.0 reads to decide which `**SECRET_*` placeholders a helper may restore.
- **mmvm bleeding edge tracks upstream** — the "develop" entry installs `github:MagicMirrorOrg/MagicMirror#develop` instead of the stale `angeldeejay/MagicMirror#develop` fork (128 commits behind, still 2.37.0-develop). Git specs get `--allow-git=root`, because npm 12 defaults to `allow-git=none` and rejected the download with `EALLOWGIT`.
- **`AGENTS.md` audit and rewrite** — corrected drift against the v3.0.0 codebase:

    - config precedence (`config.sandbox.json` > `package.json#sandbox.moduleConfig` > temp file) and the `package.json#sandbox` keys;

## v1.3.0

- **Upgraded MagicMirror dependency to v2.36.0** — formalized the pin from `^2.35.0` to `^2.36.0` and propagated the version string across all sandbox surfaces (`config/harness.config.ts`, `server/html.ts`, `client/runtime/module.ts`, test fixtures and assertions). Full contract audit confirmed zero API breaks between v2.35 and v2.36: `module.js`, `node_helper.js`, `logger.js`, `http_fetcher.js`, `server_functions.js`, and `vendor.js` all retain the same public API.
- **Config editor overhaul** — `client/vendor/module-config-editor.ts` received several changes across this release:
    - **Three-editor architecture** — rewritten from a single Ace instance to three stacked editors: a read-only prefix pane (the `let config = { … config: {` envelope), a scrollable editable pane for inner config properties, and a read-only suffix pane. Line numbers are continuous across all three. The editable pane enforces `INNER_INDENT` (6 spaces, depth 3) for display; stored values are always dedented to depth 0. `Ctrl+A` + `Delete` clears only the editable pane. A custom Ace theme (`ace-theme-harness.ts`) adapts all token and chrome colors to the active `--hns-*` token set, making the editor theme-aware without JavaScript.
    - **`header: false` renders as boolean** — `syncHeader` now detects the `"false"` string convention used by MagicMirror's attribute transport and emits a boolean `false` node instead of the string `"false"`.
    - **JS comment support** — the editable pane accepts `//` and `/* */` comments without invalidating the config. **Format** strips comments via `stripComments()` before running js-beautify; comments are not preserved through a format round-trip by design.
    - **Readonly pane hardening** — a transparent `::after` overlay blocks pointer events on prefix and suffix panes. `tabIndex=-1` on their internal Ace textareas eliminates the focus tooltip on keyboard navigation.
    - **Inline error highlighting** — on a parse failure the editable pane marks the error row with a gutter annotation and a subtle red line highlight, both cleared on the next valid keystroke. The validity indicator now shows only **Config valid** or **Config invalid**.
    - **`applyBeautify` cursor preservation** — after a format round-trip the editor attempts to restore cursor position and selection via a normalized left-context pattern match that survives whitespace changes and quoted-to-unquoted key transforms. Restoration is best-effort.
- **Journey coverage: stale artifact fix** — the reporter now detects which suites (`ui`, `integration`) are present in the current run by inspecting `testModules` paths and passes them as `explicitSuites` to `buildJourneyCoverageSummary`. Previously, a run where all journey-tagged tests crashed before producing records would exit early without overwriting the summary JSON, leaving a stale 100% score in place for subsequent badge generation.

    - **`module.data.path` now matches MM format** — `path` is now `modules/${name}/` (relative, trailing slash) matching `main.js`. Previously the sandbox used an absolute path with no trailing slash (`/modules/${name}`), causing `this.data.path + filename` concatenation to produce malformed URLs. `module.file()` is now implemented as `(this.data.path + filename).replace(/\/\//g, "/")`, a verbatim port of `module.js`.
    - **`lockStrings` protocol fully implemented** — `hide(speed, cb, {lockString})` now pushes the lock string onto `this.lockStrings`; `show(speed, cb, {lockString})` removes it and skips the show call when locks remain, matching `module.js`. Previously `this.lockStrings` was initialized but never read or written, so modules that hide via multiple independent actors (presence sensors, schedules, voice commands) would show prematurely on any `show()` call.
    - **`loadTemplates()` respects module overrides and pre-warms Nunjucks** — the base implementation now carries a `typeof instance.loadTemplates === "function"` guard (like `getTemplate` and `getTemplateData`) so a module that defines its own `loadTemplates()` is no longer silently overwritten. The default base implementation now pre-warms the Nunjucks template cache by rendering the file template with an empty data set before `start()` is called, matching `module.js` boot-phase behavior.
    - **`MM.getModules()` filter methods emit diagnostics on empty results** — `withClass()`, `exceptWithClass()`, and `exceptModule()` now log a `Log.warn` when they return an empty collection, explaining that the sandbox is a single-module environment and that the module's intent is recorded but cannot be simulated. Previously these methods silently returned empty arrays, making it opaque that the sandbox does not support sibling-module coordination.
- **D8 test suite no longer produces console noise** — the VM context for the `installGlobals creates Log` test block now receives a silent no-op console so `Log.*` method invocations during the test do not write to stdout/stderr.
- **Browser runtime now matches MagicMirror core behavior exactly** across all divergences identified by a full contract audit (`client/runtime/module.ts`, `lifecycle.ts`, `notifications.ts`):
    - **`getDom()` always returns `Promise<HTMLElement>`** — the base implementation is now a verbatim port of `module.js:82-107`. Previously the sandbox returned a synchronous `HTMLElement` (or a deferred wrapper) when `getDom` was called via `this._super()`, masking bugs that surfaced only in real MagicMirror.
    - **`hide()` and `show()` suspend/resume timing** — `suspend()` and `resume()` now fire inside the animation callback after the transition completes, matching `module.js:367-413`. Previously they fired before the animation began.
    - **`module.hidden` asymmetry** — `MM.hideModule` sets `module.hidden = true` immediately before the animation (matching `main.js:721`); `MM.showModule` sets `module.hidden = false` only after the animation completes (matching `main.js:729-731`).
    - **Header rendered as `innerHTML`** — `getHeader()` return values are now inserted via `innerHTML`, not `textContent`, matching `main.js:253`. Modules that return HTML markup in `getHeader()` now render correctly.
    - **`getHeader()` default** simplified to `return this.data.header` — matches `module.js:115-116`. The previous sandbox-specific false/empty-string handling diverged from core.
    - **`Log` object now complete** — `Log.debug`, `Log.group`, `Log.groupCollapsed`, `Log.groupEnd`, `Log.time`, `Log.timeEnd`, `Log.timeStamp`, and `Log.setLogLevel` are now exposed, matching `logger.js`. Previously calling any of these threw `TypeError: Log.X is not a function`.
    - **`MM.getModules()` filter methods** — the returned array now carries `.withClass()`, `.exceptWithClass()`, `.exceptModule()`, and `.enumerate()` as non-enumerable properties, matching `main.js:501-585`. Previously the sandbox returned a plain array without these helpers.
    - **`notificationReceived()` receives the original payload** — the sandbox previously passed a JSON clone of the payload. The original object reference is now forwarded, matching `main.js:98-101`. The clone is still used for the debug log entry only.
    - **Template preloading layer removed** — `loadTemplates()` now resolves immediately. The deferred-wrapper and sync-preload machinery (`createDeferredGetDomWrapper`, `preloadTemplateDependencyTree`, `seedTemplateLoaderCache`, `renderPreloadedTemplate`, `attachDeferredDomReady`, `hasPreloadedTemplate`, `readTemplateSource`, `extractTemplateDependencies`, `resolveTemplateDependencyPath`, `isGetDomSuperCall`) has been deleted. The nunjucks `WebLoader` handles async template fetching as it does in core.
